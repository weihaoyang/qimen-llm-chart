## 补完（同日稍后）：用 PGlite 做真引擎 SQL 验证，并查出自己两处 cast 缺陷

### 结论：真库验证的障碍解决了，不需要 Docker

`@electric-sql/pglite`（Postgres 编译到 WASM，内置 **PostgreSQL 18.3**）已加入 devDependency（`^0.5.8`）。
`pip install` 在这台机器会被 SIGTERM 杀掉、Docker daemon 起不来，但 **npm 装 WASM Postgres 可行**——以后凡是要「真 Postgres 语义」的验证，优先这条路。

### 关键注入点（可复用）

`src/lib/db/pool.ts` 把 pool 缓存在 **`globalThis.qmdjPool`**，且每次 `query` / `withTransaction` 都读这个缓存。
所以只要往这个全局槽位塞一个 `pg`-Pool 形状的适配器，**所有 repository 一行都不用改**就跑在真 Postgres 上。
适配器在 `src/lib/db/testing/pglite-harness.ts`。

**适配器里唯一的坑**：pglite 对 `SELECT` 返回 `affectedRows: 0`，而 `pg` 的 `rowCount` 对 `SELECT` 是结果集行数。
照搬会让 `if (!owner.rowCount) return null` 这类守卫在行存在时判成不存在 → 几乎所有写路径变静默 404。
按 `pg` 口径推导：`result.fields.length > 0 ? result.rows.length : result.affectedRows`。

### 最大的方法收获：「它阻塞了」是没有判别力的断言

第一版锁测试：外部持锁 + `Promise.race` 断言写者「阻塞」。**对着删掉 `FOR UPDATE` 的代码跑，它照样通过。**

原因：`replaceInventory` 结尾有 `UPDATE battle_cases SET updated_at=now()`，取**同一行**的锁。写者无论如何都会阻塞，只是阻塞点从「读之前」挪到「插入和删除之后」—— 而那正是锁要防的交错。

改用 `SELECT query FROM pg_stat_activity WHERE state='active' AND wait_event_type='Lock'` 断言**它停在哪条语句**：有锁 → 停在 `SELECT ... FOR UPDATE`；无锁 → 停在 `INSERT`。再对删锁代码跑，红得正是要的诊断。

**同理 `Promise.all` 两个写函数「制造竞争」也不可靠**（回环亚毫秒往返，经常碰巧串行）。

## 第十二批：锁顺序 —— 从「推理」变成「证据」（15:45–16:05）
